Deploying this for nothing

What the free tiers actually allow

Read off the published limits in August 2026, not from memory. Three of them change the design rather than the deployment, and one of them is a ceiling on how much product can exist at all. Everything on this board is a number somebody can check.

Service Free ceiling What this product does to it Headroom
Pinata
video storage
 1 GB · 500 files · 10 GB bandwidth · 10,000 requests/mo · 60 API req/min A 40-second clip is about 10 MB. Every farmer is asked to film weekly. ≈100 videos, ever. Roughly 1,000 plays a month. The ceiling
Vercel Hobby
api and web
 4.5 MB request body · 100 GB transfer · 1M invocations · 4 CPU-hours · 300 s max duration Uploads a 10 MB file. Serves a 173 MB model to every farmer who turns on leaf check. The body limit is already exceeded. The model alone exhausts transfer at 578 downloads. Breaks
Vercel cron
timestamp upgrades
 Hobby: once per day, fires anywhere inside the hour. A more frequent expression fails at deploy. OpenTimestamps needs the proof collected after Bitcoin confirms the block. Submission is instant. The finished proof arrives on the next daily run. Changes the copy
MongoDB M0
everything else
 0.5 GB · 500 connections · 100 ops/sec · 10 GB in and out per rolling week · pauses after 30 idle days Twelve collections. A video document with its frame hashes is about 3 KB. ~170,000 video records. Storage is not the problem; 100 ops/sec is. Fits
Render free
if the API goes here instead
 750 instance-hours/mo · sleeps after 15 idle minutes · about 1 minute to wake · no cron jobs, no background workers on free A farmer opens the app in a field with two bars of signal. First request of the morning waits a minute. There is nowhere to run the timestamp job. Wrong shape
Free LLM tiers
the agronomy chat
 Every free inference tier is rate limited per minute and per day. The exact figures move; the existence of the limit does not. One farmer asking three questions in a row can exhaust a per-minute allowance. Needs a refusal state the screen does not have yet. Missing state
The video cannot go through the API
A function request body caps at 4.5 MB and returns 413 above it. A 40-second clip is twice that. This is not a tuning problem, it is a wall.
The phone uploads straight to storage
The API issues a one-use upload URL, the handset sends the file to Pinata directly, and the API never sees the bytes in a request body.
And the trust claim survives it
The landing page promises the server hashes the bytes it actually received, never a number the phone sends. That still holds: the server pulls the stored object back and hashes it itself. It costs one download per video, well inside the budget, and it is the reason the claim is allowed to stay on the page.
A hundred videos, and then it is full
1 GB of pinned storage against 10 MB a clip. Twenty farmers filming weekly reach it in five weeks. Nothing in the architecture can be clevered around this, because deleting old videos is precisely what the product promises never to do.
What it is honestly for
A pilot with a handful of farmers, a demonstration, or a review. Say that out loud rather than opening signups and filling up in week five.
What buys room
Cap the clip at 20 s and 720p and it is about 3 MB — three times the runway for a video that still shows the crop and the edges of the plot.
The timestamp is not affected. A Bitcoin attestation covers a hash, not a file, and the hashes are in Mongo. Even if storage filled tomorrow, every date already proved stays proved.

On the screen after filming
A few hours, sometimes until tomorrow.
Usually by tomorrow. We send it off straight away; the proof comes back on a once-a-day run.
A daily cron cannot deliver “a few hours”, so the screen stops saying it.
On the admin console
“Waiting longer than a day” flagged normal behaviour as a fault. On a daily job the threshold is 48 hours.
Two smaller traps
The 173 MB leaf model must not be served from our own origin. It comes from the model host it already lives on, so it never touches the 100 GB transfer budget. Served from the app, 578 farmers would end the month.
Runtime logs are kept one hour on Hobby. The admin page says every action there is logged against a name. That has to be a collection in the database, not a platform log — otherwise the audit trail evaporates before anyone looks for it.
One more, easy to trip over: a Hobby project cannot connect to a repository owned by a GitHub organisation. This one is personal, so it deploys. Moving it under an org later stops the deploys that day.
What none of this touches
Every screen on this canvas is text, flat colour and inline SVG. No photographs, no icon font, no illustration library, no animation library. The whole set carries zero raster images.
Farmer screens use the system font stack, so a handset downloads no typeface at all — Android already ships the Indic fonts, and re-sending them would cost 35–124 KB of a metered pack for nothing. The investor and buyer pages load one web family, and only they do.
The motion is transform and opacity on the compositor. It costs no bytes and no server anything.
